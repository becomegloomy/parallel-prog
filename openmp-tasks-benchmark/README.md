# OpenMP tasks benchmark

Сравнение последовательной и параллельной версий C-программы, где параллелизм реализован через **OpenMP tasks** (`#pragma omp task`, `taskwait`). Плюс методика измерений с **10 повторами** на точку и **доверительным интервалом CI95%**.

Цель - показать, что параллельная версия не обязательно быстрее последовательной: и разобраться почему tasks дают **отрицательное ускорение** (S < 1).

## Задача

Программа делает **5 независимых экспериментов**. В каждом эксперименте над двумя массивами- `M1` (размер `N`) и `M2` (размер `N/2`) - выполняются этапы:

| Этап | Что происходит |
|---|---|
| **Generate** | Заполнение массивов случайными числами |
| **Map (M1)** | Каждый элемент `M1` = `coth(sqrt(x))` |
| **Map (M2)** | Каждый элемент `M2` = `sqrt((M2_copy[j] + M2_copy[j-1]) * e)` |
| **Merge** | Поэлементное деление: `M2[j] = M1[j] / M2[j]` |
| **Sort** | Сортировка расчёской |
| **Reduce** | Сумма синусов тех элементов `M2`, у которых частное `M2[j] / min_nonzero` - чётное, `min_nonzero`- первый ненулевой элемент после сортировки |

Итоговое значение `X` суммируется по всем 5 экспериментам.

### Что распараллелено и почему

**Параллельно:**
- Generate M1/M2, Map (M1), Merge, Reduce - независимые итерации;
- Sort - `M2` делится на две независимые половины, каждая сортируется в своей задаче.

**Последовательно:**
- **Map (M2)** - рекуррентная зависимость;
- **поиск `min_nonzero`** - первый ненулевой элемент, простой проход;
- **`merge_halves`** - слияние двух отсортированных половин, последовательный алгоритм.

## Требования

- GCC ≥ 9 с поддержкой OpenMP (`-fopenmp`);
- Python 3 с пакетами `matplotlib`, `numpy`;
- Bash.

Установка Python-зависимостей:

```bash
pip install -r requirements.txt
```

## Запуск

```bash
make            # сборка omp-tasks-bench
make bench      # 10 повторов на (N, T) → results_2.csv
make plots      # график ускорения с CI95% → speedup_ci.png
```

### Ручная сборка

```bash
gcc -O2 -fopenmp -Wall -Wextra -std=c11 src/omp-tasks-bench.c -lm -o omp-tasks-bench
```

### Ручной запуск

```bash
OMP_NUM_THREADS=4 ./omp-tasks-bench 522000
./omp-tasks-bench 522000 4
```

## Что ожидать на графиках

2 ядра, `N = 522000`:

| Потоков `T` | Время, ms | Ускорение |
|---|---|---|
| 1 | ~225 | 1.00 |
| 2 | ~250 | ~0.90 |
| 4 | ~280 | ~0.80 |
| 8 | ~230 | ~0.98 |
| 16 | ~245 | ~0.92 |

**Ускорение** - во сколько раз `T` потоков быстрее одного: `S(T) = T(1) / T(T)`.

Ключевое наблюдение: **S < 1 на всех T** - параллельная версия **медленнее** последовательной. Причины:

- **Map (M2)** и **поиск `min_nonzero`** последовательные и занимают много времени;
- **`merge_halves`** после `task`-сортировки - последовательный;
- **task-overhead** на этой задаче больше, чем выигрыш от параллельной сортировки двух половин;
- **oversubscription** при `T > числа ядер` - потоки конкурируют за ядра.
