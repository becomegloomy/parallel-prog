# ipp-omp-benchmark

Сравнение двух реализаций одной задачи обработки массивов: последовательной (Intel IPP) и параллельной (OpenMP). Плюс замер загрузки процессора при разном числе потоков.

Цель - понять, сколько реально даёт OpenMP на этой задаче, где ускорение упирается в предел и что происходит с ядрами, когда потоков больше, чем ядер.

### Что внутри

- **`ipp-parallel`** - последовательная версия на Intel IPP;
- **`omp-parallel`** - параллельная версия на OpenMP;
- **`mpstat`** - системная утилита, которая показывает загрузку каждого ядра.

### Задача

Программа делает **5 независимых экспериментов**. В каждом эксперименте над двумя массивами - `M1` (размер `N`) и `M2` (размер `N/2`) - выполняются этапы:

| Этап | Что происходит |
|---|---|
| **Generate** | Заполнение массивов случайными числами |
| **Map (M1)** | Каждый элемент `M1` = `coth(sqrt(x))` |
| **Map (M2)** | Каждый элемент `M2` = `sqrt((M2_copy[j] + M2_copy[j-1]) * e)` |
| **Merge** | Поэлементное деление: `M2[j] = M1[j] / M2[j]` |
| **Sort** | Сортировка расчёской |
| **Reduce** | Сумма синусов тех элементов `M2`, у которых частное `M2[j] / min_nonzero` - чётное, `min_nonzero`- первый ненулевой элемент после сортировки |

Итоговое значение `X` суммируется по всем 5 экспериментам.

**Что распараллелено:** этапы Map (M1), Map (M2), Merge и Reduce идут параллельно через `#pragma omp parallel for`. Важно: в Map (M2) элемент `M2[j]` зависит от `M2_copy[j-1]` — от **исходного** массива, который не меняется, поэтому гонки нет.

**Что осталось последовательным:** генерация (общий `seed` у `rand_r` дал бы гонку), сортировка (Comb Sort плохо параллелится — обмены зависят друг от друга) и поиск `min_nonzero` (последовательный проход по массиву).

### Требования

- GCC ≥ 9 с поддержкой OpenMP
- Intel oneAPI Base Toolkit (содержит Intel IPP) — <https://www.intel.com/content/www/us/en/developer/tools/oneapi/base-toolkit-download.html>
- Python 3 с пакетами `pandas`, `matplotlib`, `numpy` — для построения графиков
- `sysstat` (утилита `mpstat`) — для замера загрузки процессора

### Запуск

```bash
make            # сборка ipp-parallel и omp-parallel
make bench      # замер времени → results/results.csv
make overhead   # замер загрузки CPU → results/cpu_M{4,8,12,16,20}.csv
make plots      # построение графиков → time_execution.png, speedup.png, efficiency.png, cpu_usage.png
```

- `make bench`: `N` от 300 до 522000 (11 точек), `M` (число потоков) от 1 до 8.
- `make overhead`: `M` = 4, 8, 12, 16, 20; в фоне работает `mpstat`, параллельно — `omp-parallel` при `N = 463500`.

### Что ожидать на графиках

Типичные цифры (8 ядер, `N = 522000`):

| Потоков `M` | Время, ms | Ускорение | Эффективность |
|---|---|---|---|
| 1 | ~280 | 1.00 | 1.00 |
| 2 | ~150 | ~1.85 | ~0.93 |
| 4 | ~90  | ~3.10 | ~0.78 |
| 8 | ~70  | ~4.00 | ~0.50 |

**Ускорение** — во сколько раз быстрее последовательной версии. **Эффективность** — какая доля от идеального ускорения достигнута (идеал = 1.0).

Ускорение перестаёт расти, когда потоков становится больше, чем ядер: часть программы (сортировка) выполняется последовательно, и она ограничивает общий выигрыш. Цифры зависят от железа, но форма кривой (насыщение) сохранится.

### Ограничения

1. **Сортировка последовательная.** Comb Sort плохо параллелится, и при больших `N` он занимает большую часть времени — поэтому ускорение упирается в предел.
2. **При `N = 300` время < 1 мс.** Таймер `gettimeofday` даёт миллисекунды, поэтому получается 0. Для этой точки ускорение не определено (`NaN` в `plot_results.py`), но скрипт не падает.
3. **`ipp-parallel` — это «точка отсчёта».** Переменная `OMP_NUM_THREADS` на неё не влияет: IPP сам решает, сколько потоков использовать (для этих функций — один). Реальное ускорение — только в `omp-parallel`.
4. **Потоков больше, чем ядер — переподписка.** Когда `M` больше числа ядер, все ядра загружены на ~100 %, но ускорения нет: потоки конкурируют за процессор.
5. **`N2` в скриптах разный**: в `run_all.sh` — 522000, в `run_overhead.sh` — 463500. Замер загрузки CPU делался при `N = 463500`, близком к максимальному.

### Структура проекта

```
ipp-omp-benchmark/
├── README.md
├── Makefile
├── .gitignore
├── src/
│   ├── ipp-parallel.c     # последовательная версия (Intel IPP)
│   └── omp-parallel.c     # параллельная версия (OpenMP)
└── scripts/
    ├── run_all.sh         # замер времени: последовательная vs M потоков
    ├── run_overhead.sh    # замер загрузки CPU через mpstat
    ├── parse.py           # mpstat .txt → .csv
    ├── plot_results.py    # графики времени, ускорения, эффективности
    └── plot_results2.py   # график загрузки CPU
```

Папка `results/` создаётся автоматически при запуске и в git не коммитится — её содержимое воспроизводится командами выше.
